# Research Workbench 阅读与证据升级设计

日期：2026-10-03。状态：用户已批准进入实施计划；产品代码尚未授权实施。阅读与证据支持自由探索，科研质量状态仅作可视化提示；实际执行、外传与文件校验仍受技术安全约束。

## 1. 目标和边界

目标是在现有 Android、macOS、Windows 本地离线研究工作台上，让研究者能从论文原文找到可复核的证据，把证据带入问题比较、实验任务和论文写作。第一阶段优先解决阅读导航、定位、摘录、检索及 OCR；第二阶段串起跨论文证据与实验判断；第三阶段加入翻译和可选的出处明确的 AI 辅助。保留现有研究目录/ZIP 导入、原始快照、Markdown/PDF 阅读、精读笔记、提纲、任务及结果包流程。原始 PDF 的字节始终不可变；抽取文本、OCR、图表裁切、解释、译文和 AI 输出都是带来源的派生数据，不能覆盖原文或自动成为已核验证据。

本规格只改造 `research-workbench`。未来统一外壳可以提供工作台、消息中心、个人中心、数据中心、智能助手、系统设置和应用注册，但这些模块不是本次建设范围。离线人工文件交换与显式启动的 LAN 单文件传输仍可用；不以云、账户、复杂多端同步或插件市场为第一阶段前提。任务包内的代码和命令仍只作为规格数据，不由工作台自动执行。

## 2. 现状证据与选择

当前仓库的 `pubspec.yaml` 锁定 Flutter、SQLite、`pdfrx 2.6.5`/`pdfrx_engine 0.6.1`、`flutter_markdown_plus`；含 `android/`、`macos/`、`windows/` 平台工程。`lib/main.dart` 打开应用私有目录；`lib/core/store.dart` 的 SQLite 表已有项目、文档、条目、任务修订、运行、笔记、提纲以及近期新增的论文绑定/文档哈希迁移。`lib/core/exchange.dart` 快照原始材料并校验 ZIP、相对路径、文件数量和大小；`lib/core/lan_transfer.dart` 是用户显式启动、限时、单文件的 LAN 传输。`lib/reader/reader_page.dart` 已能显示 Markdown/PDF、翻页、缩放、打开目录内 Markdown 链接，手动记录页码、引句和笔记并关联提纲。`lib/app/workbench_app.dart` 的文库搜索只匹配文件相对路径和已导入条目的标题/JSON 字段，不索引 PDF/Markdown 正文；阅读器本身也没有目录大纲、文内搜索、阅读位置保存、区域选取和 OCR。关系页另有记录搜索，不等同于全文搜索。现有笔记中的引句由人粘贴，尚无文字/区域锚点回跳或原文校验。写作导出仅包含提纲引用、已接纳运行与笔记。

`docs/design.md` 是现有 MVP 边界；正在变化的 `docs/research-skill-integration.md` 设计 research-skill V2 格式、修订、论文绑定与草稿回写。本规格复用其文件绑定和回写边界：工作台不直接改原研究日志，不把 OCR 或阅读行为提升为科学认可。两份设计需在实施计划阶段核对迁移编号和字段，不能覆盖当前工作区其他未提交改动。

比较了三种路径：

| 路径 | 收益 | 成本/风险 | 结论 |
|---|---|---|---|
| 在现有 Flutter 工作台增量扩展阅读/证据层 | 复用快照、任务、提纲、导入导出及真机可运行界面 | 阅读器与 `workbench_app.dart` 较集中，需拆清服务边界 | **推荐**，先完成业务闭环 |
| 抽通用核心后另写科研应用 | 有利于以后平台化 | 现在重复搬运数据与界面，迁移风险高 | 待统一平台契约稳定再评估 |
| 先建统一外壳/公共服务再做阅读 | 平台一致性强 | 延迟最急迫的科研阅读，接口在缺少使用案例时易过度设计 | 本轮不选 |

## 3. 分阶段能力

### 第一阶段：可定位、可检索的精读

1. **阅读导航与位置。** PDF 提供页缩略图/页码跳转和从文内标题生成的大纲；Markdown 使用标题大纲。记录每份文档的上次页码或标题锚点、页内相对滚动位置、缩放值及文档哈希；下次打开可选择继续。页码始终明确区分 PDF 物理页与论文印刷页。仅在原哈希一致时精确恢复；换版显示旧位置待复核，不能静默跳到可能错误的页。
2. **文内与项目搜索。** 对 Markdown 正文和可抽取的 PDF 文本建立可重建的本地索引，OCR 页再补入带 `source=ocr` 的索引。文内搜索显示页码/标题、上下文并可跳回；项目搜索可按论文、主张、正文、笔记和来源类型筛选，结果只属于当前项目。索引是派生数据，文档哈希或 OCR 模型版本变化时仅重建受影响文档；不索引未被导入的私有文件。搜索失败或索引未完成时仍可阅读原文，显示状态，不把“无索引”误报为“无结果”。
3. **原文定位证据卡。** 从原文选择文字、从 OCR 框选择文字或手动指定区域后生成草稿卡，至少显示文档/论文修订、文档 SHA-256、PDF 页码或 Markdown 标题、页内归一化区域、精确引句、前后文、抽取方式、定位可信度、创建时间。下方另设用户解释、是否支持/不支持某主张、待复审状态。点击卡片返回原文并高亮位置；坐标失效或引句不匹配时标“定位待复核”，不得悄然挪到类似文本。沿用现有笔记/提纲关系，可从旧笔记生成无精确区域的兼容卡，原记录不删除。
4. **图表与区域摘录。** 在 PDF 页上框选归一化矩形，保存独立的裁切图像、来源页/哈希/矩形、用户题注及可选 OCR 文字。图像是派生副本；原 PDF 不写入批注。支持从证据卡回到原页定位。对于跨页图表、旋转页、过小区域，要求重新选取或标明限制，不推断图表含义。
5. **文字 PDF 优先，扫描页按需 OCR。** 先使用当前 `pdfrx_engine` 的 `PdfPage.loadText/loadStructuredText` 取得文本及字符边界；低文本密度或用户指定的扫描页，渲染页后走 `OcrPort`。选定 PaddleOCR 为首选离线 OCR 实现，但 Android、macOS、Windows 的模型、原生运行时、体积、性能、授权和打包须分别验证。实施可采用各平台适配器，不能把桌面 Python 方案当成三端已支持。模型必须随明确安装包或经用户明确本地导入，不在后台下载；无可用模型时提示并保留文字 PDF 阅读、手动摘录。OCR 返回文字、区域、置信度、语言与模型版本；结果需人工核对，不能自动判定论文主张。优先只处理正在阅读的页/用户选区，后台批量索引需显式启动和可取消。

### 第二阶段：问题驱动的证据与实验链

项目问题可建立比较板：选择同一问题下各论文的证据卡，按研究对象、方法、指标、结论、局限和互相支持/冲突/未知并排展示；每个单元都能回到原文。关系使用明确 ID、文档哈希及论文 `id+rev`，不能仅凭标题相似度自动绑定。

从证据卡创建或关联现有有版本任务；结果记录绑定 `taskId+revision+runId`、数据/代码/环境摘要、原始产物及人工判断。导入结果先保留原记录，再由人确认“关联为证据”，科学结论还需另行复审。比较板显示任务规格、结果状态与人工判断的不同层次；不把运行 `completed` 等同科学有效。继续复用离线任务/结果包和 Markdown 报告，而非另设不兼容交换格式。

### 第三阶段：翻译与有出处的辅助

按段落生成独立译文，保存原段落锚点、语言、术语表版本、译者或工具、时间及人工修订，双栏能回到原文；译文不能替换原引句。桌面可选 BabelDOC 作为外部 PDF 翻译适配器，输出另存派生 PDF，并在引入前审查其 AGPL-3.0 许可及部署/服务依赖。可选 AI 回答只基于用户选定的本地证据卡和可回跳原文输出引用；无法找到依据时明确回答“证据不足”。联网模型需要单次明确授权和可见的发送内容，本地离线路径始终可用。AI 与翻译输出不能自动接纳为科学证据。为未来 AI-native 外壳，研究应用对 AI 暴露与界面一致的业务命令和按项目/文档/证据范围裁剪的上下文接口，所有写操作仍走相同校验与人工确认。知识库具体引擎由后续平台设计决定；本规格不选定 Obsidian 核心、向量数据库或新缓存框架。

## 4. 数据、接口与迁移

现有 SQLite 与快照继续支撑独立工作台。建议在**当前仓库实际最新 schema 之后追加迁移**，不编辑旧迁移；与 research-skill 集成分支可能新增的迁移协调编号。新增对象按职责分开：`reading_positions(document_id, document_sha256, pdf_page, heading_anchor, scroll_ratio, zoom, updated_at)`；`text_layers(document_id, document_sha256, page_or_anchor, source, engine_version, text, geometry_ref, indexed_at)`；`evidence_cards(id, project_id, document_id, document_sha256, paper_id, paper_rev, source_type, locator_json, quote, context, interpretation, review_state, created_at)`；`evidence_regions(card_id, normalized_rect, image_blob_ref, image_sha256)`。大块文本/图像存应用私有派生文件，SQLite 管索引、关系和版本；每条派生内容记录输入 SHA-256、算法/模型版本，原快照仍不可覆盖。项目内搜索可先以本地 SQLite FTS 索引实现，但 FTS 支持、中文分词和三端性能要在实施前验证；索引可以删除重建，业务记录不能因重建而丢失。

迁移过程先备份/打开旧数据库并追加表，旧 `notes`、`outline`、`tasks`、`runs` 和导入快照保持原样。旧笔记保留现有 `locator/page_number/quoted_text`；只有用户打开或显式转换时才生成证据卡，精确区域为空、状态为“待定位/待复核”，不得倒填 OCR 证明。现有已导入文档用保存的文档哈希或重新校验一次原快照建立索引；发现快照哈希不符时暂停关联并提示。后续再导入同一项目的快照迁移遵循 `docs/research-skill-integration.md` 的待复核规则，不因文件名相同就继承原文定位。

代码边界建议为 `DocumentTextPort`（文字抽取、页渲染）、`OcrPort`（按需 OCR）、`ReadingIndex`（仅派生索引与定位）、`EvidenceRepository`（卡片与关系）、现有 `ResearchExchange`（显式包交换）；阅读器消费这些接口而不直接承担全部存储与索引。第一阶段先用本地适配器连接当前 SQLite/快照和拟实现的 PaddleOCR 适配器。为未来统一平台只保留窄契约：研究应用注册带命名空间的领域 schema、业务校验与消息/数据中心展示入口；基础平台拥有实际文件/结构化数据的存储、管理、包交换、多端与 LAN 交换，并通过受控存储/传输端口供应用读写；接口平台负责第三方连接器、字段映射、验证和交换任务，由基础平台持久化交换记录。当前独立应用不依赖统一外壳运行，未来也不预设“每个业务应用永久独立持有数据库”。OCR 可经公共能力端口提供，拟建的 PaddleOCR 本地适配器保留替换空间。基础平台未来可为各应用提供命名空间下的知识目录、结构化记录及派生缓存，但目录分工与知识引擎仍由平台方案决定；本阶段不迁移实际数据所有权。

## 5. 已发现的结果包回导冲突

2026-10-03 在 V2324A Android 16 上，用合成任务 `synthetic-task-20261002` 手工建立并完成运行 `cfa88634-bf9c-4f08-81a8-3e054b108823`，导出 612 字节 ZIP 到 `Download/ResearchWorkbenchSynthetic/SYNTHETIC_MANUAL_RESULT_20261003.zip`；同机原样回导提示 `FormatException: Run ID already exists with different contents`。包内 `result.json` 与通过只读 SQLite 查询取得的同 ID 行在业务字段（任务、修订、状态、指标、日志、产物、结论）一致；数据库 `data` 额外含 `_localManual:true`，包中没有。`accepted=0` 是独立列，未参与此对比；没有时间字段和附件路径差异，产物均为空。另一个实现缺陷是按 `jsonEncode(old) != jsonEncode(data)` 比较字符串，键顺序也影响判定；此次两者的 `conclusion` 与 `artifacts` 字段顺序不同。证据：`lib/core/store.dart` 的 `startManualRun` 写入 `_localManual`，`lib/core/exchange.dart:628-638` 导出公开字段，而 `:724-744` 只移除 `_snapshotPath` 后逐字比较。`lib/app/workbench_app.dart:1114-1140` 只给非本地手工记录显示“确认关联为证据”，因此同机未成功回导时，这条原始手工记录无法完成接纳。这是同机重复导入路径的已复现故障；正常跨设备首次回传若接收端无该 runId，会走新插入分支，现有单手机试验没有证明它失败，也未证明它成功。

建议在正式实施计划中把此项列为先修回归：比较标准化的**交换业务字段**而非 JSON 字符串或本地元数据；同 ID、同业务内容的重复导入应幂等返回已有记录并保留独立的接纳状态；同 ID、不同业务内容仍报冲突并保留两份原始包供排查。测试至少覆盖本地导出再导入、异设备首导入、重复导入、已接纳后重复导入、内容真正不同、带附件清单及任务修订不匹配。不得靠删除/改写已有运行记录让测试通过。

## 6. 第一阶段验收

- 三端分别从旧库升级后打开原有研究、笔记、提纲、任务与结果；旧文件 SHA-256 不变，失败可回到旧数据库副本，不丢用户记录。Android 需真实设备；macOS/Windows 需各自原生构建与实际文件选择/保存验证，单手机结果不能代替桌面或双设备验收。
- 文字 PDF 与 Markdown 的大纲、页/标题跳转、上次位置、文内查找可用；项目搜索按当前项目返回正文、笔记、记录，命中点能回到准确原文，未索引页有清晰状态。
- 文字 PDF 先抽取可选文字及坐标；扫描页使用经用户选用的离线 PaddleOCR 适配器识别，展示 OCR 来源和不确定性；无模型、低置信度、旋转页与多栏版式有可恢复提示，不生成伪精确引句。
- 文字证据卡和图表区域卡能保存、复开、跳回并显示哈希/页/区域；用户解释单独编辑，修改解释不改变原文引句或原快照；文件换版后旧定位转待复核。
- 对已接纳的旧运行及现有笔记的报告输出做回归。结果包回导冲突先修后，用两个真实安装实例和合成包验证一端导出、另一端首次导入、人工接纳、报告引用；单机导出回导单列为幂等回归。工作台始终不执行任务命令。

本轮设计不证明 PaddleOCR、BabelDOC、桌面运行或双设备回传已经集成。当前真机证据仅覆盖单部 Android 手机上的合成材料与手工记录；两条同任务合成手工运行 `0.82/0.73` 已在横向比对表可见，但均未接纳，因此导出的 Markdown 报告只有项目概要和空的精读笔记标题。合成证据位于 `artifacts/final-2026-10-02/native-2026-10-03/`（本地忽略目录），不可当作真实研究结论。

## 8. 与研究案例融合的先后依赖

[融合案例规格](2026-10-03-integrated-research-case-design.md)复用本文的原文定位证据卡、文档哈希、图表摘录与项目搜索，不创建第二套阅读证据库。案例最小闭环可先读取现有笔记、当前 skill V6.6 JSONL 与 V6.4 历史输入，以及 task/run 包；本文第一阶段完成后再把精确证据卡接入同一案例引用。本文第二阶段的跨论文比较归属于案例的问题/候选决策视图，不能独立维护另一套候选、计划或执行历史。结果包同机回导冲突是融合案例跨设备人工接纳验收的先修项；PaddleOCR、翻译和 AI 均不是方法规则或最小执行移交的前置条件。融合规格保持 MethodSpec、可选轻量 WorkflowDefinition、ResearchCase/PlanVersion、ExecutionAttempt 分层，既不强制逐步填表，也不引入流程引擎；skill 保持独立可用。
